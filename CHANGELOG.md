# Changelog

All notable changes to Soupy will be recorded here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project tries to use [Semantic Versioning](https://semver.org/spec/v2.0.0.html) — though for a single-deployment Discord bot, that's a guideline, not a contract.

## [Unreleased]

### Added
- **The web panel starts, stops and watches the Flux server.** `flux_server.py` had to be started by hand in its own terminal, which also held the only copy of its log. `web/services/flux_runner.py` runs it as a child of the panel: a Flux server card on the Overview tab has Start, Stop, Restart and the recent log, every line also goes to `logs/flux_server.log` and to the live log marked `[flux]`, and `FLUX_SERVER_AUTOSTART=true` brings it up with the panel. A server started by hand is shown as running outside the panel and left alone. New routes: `GET /api/flux/status`, `GET /api/flux/log`, `POST /api/flux/start`, `/stop`, `/restart`.
- **`/flux` takes `fancy:true`.** Soupy writes the fuller prompt first and generates once. About 37 times in the archive a short prompt was generated and then sent straight to the Fancy button, which threw the first picture away.
- **A Flux picture's archive row says how it was made.** `media/images/index.jsonl` now records the model (as reported by the server), steps, guidance, strength, the source image, the prompt a Fancy rewrite started from, and the seconds it took. The Media tab's lightbox shows them, with a link to the source image.
- **New env vars `FLUX_CACHE_LIMIT_GB`** (default `2`) **and `FLUX_SERVER_AUTOSTART`** (`true` in the template, off when absent). The installer asks about the second on the Flux path.
- **`tools/prune_flux_sources.py`** removes the copies of archived pictures from `media/flux_sources` (see Fixed). It reports by default and deletes with `--delete`.
- **The Model & Personality tab shows what the model server is doing.** The Chat model card reads LM Studio's own list: whether the chat model is loaded, the context length it was loaded with, and the chat prompt budget (`CONTEXT_WINDOW_TOKENS`) as a share of it, with a warning above 85% and an error above 100%. A second card lists every loaded model with what Soupy uses it for (chat, images, embeddings) and its size.
- **A model switch says what it will do before it does it.** Apply asks the server for a plan and shows it in the confirm dialog: which models LM Studio unloads and loads, which stay loaded and why, the total it will hold, and the lines written to `.env-stable`. When the chat model has also been reading images, a checkbox moves `VISION_MODEL` with it so the old model can be unloaded.
- **The prompt editor covers all nine prompts.** It had two (`BEHAVIOUR`, `BEHAVIOUR_SEARCH`). It now lists every prompt the bot loads, including article posts, `/9ball`, both Fancy rewrites, both random prompts and the negative prompt, each with what it is used for and where its text comes from. Unsaved edits are kept per prompt and marked, the browser asks before a reload discards them, and Cmd/Ctrl+S saves.
- **Saving a prompt keeps the version it replaced** in `prompts/backups/` (the newest 20 per prompt, gitignored). "Use shipped default" moves the custom file there and returns to the shipped text, which is shown beside a custom prompt for comparison.
- **The editor says when the running bot has an older prompt.** The bot reads prompts once, at startup. A prompt saved after that gets a note and a restart link.
- **`POST /api/prompts/reset`**, and `dry_run` on `POST /api/lm-studio/switch-model`. `tests/fake_lm_studio.py` is a stand-in for LM Studio's REST API, used by the tests and runnable on a port for trying the panel by hand.
- **The dashboard's Database tab is rebuilt around reading the archive.** It was three stacked panels: a table that needed "Load rows" pressed, with free-text boxes for channel and user IDs and a raw-JSON drawer under it, then a second table of profiles whose detail was the whole profile as one block of text followed by its JSON twice. It is now one server picker and three views. **Messages** loads on its own and filters as you type: search (message text, image descriptions, link summaries), channel, member, a date range, "has image" / "has link", newest or oldest first. A message opens in place with its full text, what Soupy saw in its image, its link summary, and a "Show conversation" button that loads the messages around it in the same channel. **Profiles** lists the members with a profile beside the open one, which reads as its overview, "how they talk", and dated items under headed sections; chips filter to one section, a box filters the items, and the list's search runs across every profile's text. **Maintenance** holds the profile job (with a progress bar and buttons that are enabled only when they apply), archive scans (run one, the automatic interval, recent scans) and the RAG index.
- **Images open in a lightbox.** The Media tab's grid used to fill a caption panel below itself, off-screen on a full page. A click now opens the image over the page with who posted or requested it, the channel by name, the local time, the whole description or prompt, size and seed, and buttons to copy the text or open the file. The arrow keys step through the archive and turn the grid's page with them, Esc or a click on the backdrop closes it, and the grid marks the image you were last on. The grid shows 60 per page, filters by kind with counts, and has a search over descriptions, prompts, names and filenames (`q` on `GET /api/archive/images`).
- **Soupy's memory of itself can be read in the panel.** It is the first entry in the Profiles view, laid out like a member profile from `data/self_md/guild_<id>_self.json`. Until now the panel showed only its item count.
- **New endpoints for the above:** `GET /api/profiles/get/{guild_id}/{user_id}` (one profile in sections; `self` for Soupy's memory), `GET /api/database/members/{guild_id}`, `GET /api/database/context/{guild_id}/{message_id}`, and `after` / `before` / `order` on `GET /api/database/explore/{guild_id}`. The queries live in the new `web/services/browse.py`, on connections opened with `PRAGMA query_only`.
- **Soupy knows what time it is, and how old things are.** The chat prompt carried no clock, channel history arrived as one unbroken conversation, and retrieved memory had either no date or a raw UTC timestamp. Across 2,643 archived replies, about four in ten were written over a history window that reached back six hours or more, read as if it were still going on; almost nobody asks the time (3 direct questions ever), so the gain is knowing what is stale. The new `soupy/timeaware.py` holds the pieces, all pure functions of the datetimes passed in: a `TIME` block at the end of the system prompt (`right now it is tuesday, october 6, 2026, 6:14 am PDT (early morning)`, in `TIMEZONE`, with rules to use it only when it matters and not to remark on anyone else's hour); a marker on each stretch of history separated by an hour or more (`[chat from yesterday evening]`), added only when the window isn't one live stretch, so a live conversation's prompt is unchanged; and one line on the message being answered when it broke a silence. Ages are worded in code because the 12b model is unreliable at date arithmetic. Markers are their own `user` entries so they never sit inside Soupy's turns, they go in after the RAG query is built so they are never embedded, and `clean_response` strips one if the model echoes it. Measured cost: the LLM call takes prompt tokens ÷ 239 seconds, so the roughly 250 tokens this adds is about a second on a 23 s median call.
- **Memory says how long ago.** With the same clock, `fetch_rag_context_for_query(now=...)` heads each retrieved conversation with its age (`--- related conversation 1, from about 3 weeks ago`, plus the year once it is a year or more old) and ends each keyword line with an age instead of a raw UTC timestamp. Ages are read off the Discord message ids already stored with every chunk, so there is no reindex, and they are exact where the archive's UTC `date` column is a day ahead for anything said in the evening (24% of archived messages). Profile and self-memory items in the chat render say `(about 5 months ago)` instead of `(May 2026)`, with `again about 3 weeks ago` when a later message confirmed them; under a week they stay vague (`in the last day or two`) because item dates are UTC dates. The profile build prompt, stored documents and `/soupyself view` keep full dates.
- **Runtime flag `time_awareness`** (`data/runtime_flags.json`, on unless switched off), with a "Time awareness" switch in the dashboard's knobs and a `time_awareness` field on `POST /api/runtime-flags`. Off, every caller does what it did before. No new env vars; `TIMEZONE` is the clock's zone.
- **Soupy's Bluesky posts go through an anti-slop gate.** Its replies, quote-post commentary and original posts were carrying the shapes that out a draft as AI: "not x, it's y", a main clause with two trailing comma-fragments, a slogan closer, deck words ("nuanced", "underscores", "a testament to"), and "just" in most posts. The new `soupy/slop.py` holds both halves of the fix: `SLOP_RULES` is appended to `COMMENT_SYSTEM`, `QUOTE_POST_SYSTEM` and `ORIGINAL_POST_SYSTEM`, and `slop_tells()` reads the drafts back and names what they still carry. Each pipeline already wrote three candidates, so `_drop_slop` keeps the ones with the fewest tells and the existing LLM judge picks between those on substance; nothing clean means the least sloppy drafts go through with a log line, never an empty list. `rank_candidates` also counts a repeated opener as a tell, checked against the last eight things Soupy posted in that bucket ("it is funny how ..." opened three of its last six posts). The rules govern shape only: the PERSPECTIVE blocks carrying Soupy's pro-worker, anti-war, punch-up-at-power politics are untouched, the prompt says so in as many words, and `tests/test_slop.py` pins both that and the fact that no political line trips the detector. Adapted from the stop-slop skill by Hardik Pandya (MIT).
- **Soupy's memory of itself, built the way member profiles are.** The new `soupy_database/self_profile.py` reads Soupy's own archived messages, each with up to three member messages from the 15 minutes before it, and folds them into a version-2 document of a new `SELF` kind in `profile_document.py`: dated, first-person items in Personality, Lately, People (how Soupy gets along with each member, at most 4 items per person), Opinions, Likes & dislikes, Running jokes, Moments, About me, Habits, and Unsure. It shares the member builder's pass loop (`run_edit_passes`, extracted from `refresh_user_profile`), so passes are sized to LM Studio's loaded window, save as they go, split on failure, and wait for chat. Only what Soupy said counts: a People item must name someone who is in that exchange, agreement given to keep a chat going isn't an opinion, and slash-command output (search / weather / stock embeds, 8-ball and 9-ball answers) is never read. The memory lives in `data/self_md/guild_<id>_self.json` and is rendered into the existing `guild_<id>.md`, `_core.md` and `_anchor.md`, so the identity line in every reply, `/soupyself`, and the musings and Bluesky prompts read it with no change. The old SELF.MD files are copied to `data/self_md/v1_backup/` before a server's first build, and nothing from them is imported.
- **When it updates.** At the end of every profile job (manual or nightly), once Soupy has `USER_PROFILE_NIGHTLY_MIN_NEW_MESSAGES` new messages or has no memory yet; the nightly refresh queues a job for it even when no member needs one. `/soupyself refresh` and the dashboard's Soupy's Memory card queue a refresh the bot runs between members.
- **What a reply sees.** The identity line is the memory's first-person overview (whole sentences within `SELF_MD_ANCHOR_MAX_CHARS`). Through RAG, Soupy gets its items about the asker and about the member being discussed, then the items closest to the message by embedding (each item is embedded into `self_chunks` when a build finishes) or shared words, within `RAG_SELF_KNOWLEDGE_MAX_CHARS`. Unrelated memories never fill the budget, and Habits and Unsure are never shown. Servers without a memory yet keep the old SELF.MD chunks.
- **Member profiles, version 2: dated, sectioned, and built from the whole archive.** Every profile item now carries the date it came up in chat (the message's date, not the build date, so a rebuild over years of history keeps real dates). Sections were reorganised around capturing the person: personality traits, what's going on lately, how they treat Soupy, family & home, life events, work & school, location, what they own, opinions & pet peeves, politics, hobbies, media, relationships with other members, running jokes & nicknames, signature phrases, discussion topics, channels, and a low-confidence "unsure" list — each with a cap enforced in code. The document model lives in the new `soupy_database/profile_document.py` (pure functions) and the prompt, edit-list JSON schema, and context budget in `soupy_database/profile_llm.py`.
- **Nightly profile refresh.** `profile_jobs_loop` in the bot queues a refresh at `USER_PROFILE_NIGHTLY_HOUR` (default 4 AM local) for members with at least `USER_PROFILE_NIGHTLY_MIN_NEW_MESSAGES` new messages, updates first and unbuilt profiles after, under a `USER_PROFILE_NIGHTLY_MAX_MINUTES` time limit (default 180). Every pass saves, so a run that hits its limit or a bot restart resumes where it stopped. Toggle with `USER_PROFILE_NIGHTLY_ENABLED` (default on); the dashboard has a Profile Refresh loop card.
- **`soupy/llm_gate.py` — one big LLM call at a time.** Chat replies (for the whole reply), profile-build passes, SELF.MD reflection, and the musings / dailypost / bluesky / search LLM calls share one async lock. Profile passes size themselves close to LM Studio's loaded context window, and a single request can use all of it, so overlapping large prompts could hit the ceiling and take LM Studio down. The lock is re-entrant per task. While a pass is in flight, a waiting chat reply shows the typing indicator, and for ten minutes after any chat activity passes read at most `USER_PROFILE_BUSY_PASS_MESSAGES` (40) messages so replies never wait long.
- **`soupy/scheduling.py` — shared scheduling primitives for the autonomous loops.** `dailypost`, `bluesky`, and `musings` each carried their own copy of "pick a random time in a local-time window" and "persist today's schedule to a JSON file under `data/`", and the copies had drifted: two wrote non-atomically (a crash mid-write left a truncated schedule), all three handled a bad hour pair differently, and all three built window bounds with `.replace(hour=...)` — which raises `ValueError` for hour 24, one plausible config value away from killing the calling loop. The module exposes `window_bounds` / `random_time_in_window` (wall-clock correct across DST, and 24 means midnight), `parse_aware` (rejects non-strings and localizes naive timestamps instead of raising `TypeError` at the first comparison), and `load_json_state` / `save_json_state` (atomic tmp+`os.replace`, and `save` **returns a bool** so callers can tell a failed write from a successful one). All three cogs now use it. Only the primitives are shared — each cog's schedule *shape* stays local, since one type covering "a time", "two channel+slot events", and "a list of (time, action) pairs" would cost more than the duplication did.
- **New env vars `MUSING_HOUR_MIN` / `MUSING_HOUR_MAX`** (default `6` / `20`, the latter exclusive and allowed to be `24`). The daily musing window was briefly hardcoded as module constants in `soupy/cogs/musings.py`, which inverted the project's config model — every other tunable routes through `.env-stable` → `soupy/settings.py` → the web env editor. It does again.
- **The dashboard's Musings loop card now shows something.** `web/static/dashboard/dashboard-app.js` has rendered a card bound to `timers.musings` since the loop existed, but nothing ever wrote that slot, so it was permanently blank. The cog now publishes `enabled`, `interval`, `next_run`, `last_run`, and a new `last_status` into `bot._timer_state["musings"]`, derived from the persisted daily state so it stays correct across a restart rather than only reflecting transitions the current process happened to see. The card renders `last_status` as its today-line ("Posted today", "Skipped — window had closed", …).

### Fixed
- **Remix on an edited Flux picture redoes the edit.** Remix, Fancy, Edit and the shape buttons all ran the picture's prompt as text-to-image, and on an edited picture that prompt is an instruction ("make it a theme park"), which drew something unrelated. A result now remembers its source image. Remix runs the same change on the same source with a new seed, and Edit prompt redoes the step with a changed instruction. Fancy and the shape buttons are left off a picture made from another one; on pictures posted before this they answer with an explanation. 🖼️ Change image still starts from the picture it sits under, so a chain of edits runs A to B to C.
- **Fancy rewrites the prompt that was typed.** A second click on Fancy rewrote the first rewrite. The result now shows both (`**Original:**` above `**Prompt:**`), and Fancy, Remix and the shape buttons carry the original along.
- **Remix and Fancy keep the clicked picture's shape.** Both came out wide whatever was clicked. R-Fancy and R-Keyword, which make an unrelated picture, are still wide.
- **The panel's image-backend status is real.** `sd_server_online` was set to `True` at startup and never updated, so the SD dot was always green, and nothing reported Flux at all. The bot now checks both servers (Flux every 15 s, SD every minute) and the status bar has a Flux dot. `/status` lists the Flux server too.
- **The Flux server's memory use during a run is about half.** MLX keeps freed GPU buffers for reuse and lets that pile grow with the machine's RAM. `flux_server.py` now caps it (`FLUX_CACHE_LIMIT_GB`, default 2). On a 64 GB M1 Max a 1392x752 klein run went from about 31 GB to 16 GB and from 41 s to 34 s, with a byte-identical PNG.
- **`media/flux_sources` no longer fills with copies of the archive.** Every result was saved there as well as in `media/images`, for the 🖼️ button to read: 861 MB of the folder's 870 MB on the maintainer's install. The button reads the archive, and the folder holds uploaded source images only, one file per distinct upload.
- **A Flux server error says why.** The bot reported "HTTP 500" and dropped the server's message. It now shows it (for example Metal's buffer-size refusal).
- **`FLUX_ENABLED` does what it says.** Nothing read it. With it off, `/flux` is not registered, the buttons under older Flux pictures answer that Flux is off, and nothing checks the Flux server. **Upgrading:** set `FLUX_ENABLED=true` if `/flux` was in use with the line left at the template's `false`.
- **The negative prompt is no longer sent to Flux**, which has none and ignored it. The prompt editor's label said it went with every image request; it now says Stable Diffusion.
- **The note a button click leaves is removed when the picture arrives.** Each click left a private "🛠️ ..." message for good. The note now says how many jobs are ahead and about how long the wait is (learned from the runs since the bot started), and is deleted when the job ends.
- **The 🖼️ img2img button under a Flux image follows instructions.** It ran noise-mix img2img, which reads the text as a description of the whole picture, and every prompt typed into it was an instruction ("make it pixar style", "add an alien to the scene", "The horse should have only 4 legs."). The result was the same picture again or an unrelated one. With `FLUX_EDIT_ENABLED` on, the button now edits the displayed image through the Klein edit pipeline. Its dialog asks "What should change?" and has an optional Strength field; a strength runs noise-mix img2img instead, where the text describes the picture wanted. Without the edit pipeline the dialog is as before.
- **img2img strength is a range, not three settings.** `flux_server.py` passed the bot's 4 steps straight to mflux, which starts an img2img run on a whole step of the schedule. Strength up to 0.25, up to 0.5, and everything above were the only settings, and the last began from 90% noise. `_img2img_schedule` stretches the schedule so the requested steps cover the last `strength` of it: 0.1 starts FLUX.2 klein from about 26% noise, 0.5 from 76%, 0.7 from 86%, and a run always does `FLUX_STEPS` denoising steps. At 4 steps, 0.8 and above are one setting. Takes effect when `flux_server.py` restarts.
- **`/flux` with an image honours its `strength` option.** It was ignored whenever `FLUX_EDIT_ENABLED` was on. An image with a strength now runs noise-mix img2img at that strength; an image without one is edited by instruction, as before.
- **A request about a picture never turns into text-to-image.** When the saved copy of the source image could not be read, the prompt was generated on its own. The 🖼️ button now passes the message attachment as well, and the request fails with a message when neither can be loaded.
- **Opening the prompt editor and pressing Save rewrote the prompt.** The editor reformatted the text on load (a tidy-up written for prompts stored on one line in `.env-stable`) and saved the reformatted version. On the current chat prompt that split the last sentence into two paragraphs; the search prompt went from 2 lines to 43. The editor now shows the file as stored and saves it byte for byte.
- **Switching models could leave two copies loaded.** The switch refused to unload the vision model. With one model doing chat and images (the default setup), reloading it at a new context length loaded a second copy beside the first, and the bot kept using the old one. The plan now reloads the model whatever else it is used for.
- **The context-length field was two settings in one.** The same number was sent to LM Studio as the context length and saved as `CONTEXT_WINDOW_TOKENS`, the chat prompt budget. Pressing the button with the saved budget in the field reloaded the model at that smaller context, and typing the real context length made the budget equal to it, with no room for a prompt that tokenizes denser than estimated. They are separate fields now and the budget is checked against the context length.
- **A failed load still repointed the bot.** When LM Studio could not load the model, the old one had already been unloaded and the panel saved the new name and restarted the bot anyway. A failed load now reloads what was unloaded, saves nothing, and reports LM Studio's error.
- **The bot kept running while its model was swapped.** A reply or profile pass sent mid-switch hit a model that was half unloaded. The bot is stopped first and started after.
- **Embedding models were offered as chat models**, and the model list was a hand-kept `AVAILABLE_MODELS` that had drifted (26 names, 12 real). The list comes from the model server and leaves embedding models out. `AVAILABLE_MODELS` is the fallback when the server can't be reached; the tab offers to update it, and no longer restarts the bot to save it.
- **A prompt typed into the env editor overrode the prompt file.** `/env` showed empty fields for `BEHAVIOUR` and five other prompts. Text saved there became a variable that the bot prefers over `prompts/<name>.txt`, and the prompt editor's own saves then did nothing. Those rows now point to the prompt editor, and the prompt editor is read-only for a prompt that `.env-stable` overrides and says how to move it.
- **Fresh installs could not edit six prompts.** `.env-stable.example` still set `BEHAVIOUR`, `BEHAVIOUR_SEARCH`, `9BALL`, `FANCY`, `RANDOMPROMPT` and `SD_NEGATIVE_PROMPT`, so every new `.env-stable` overrode the prompt files. The template no longer sets them. Their text was identical to the shipped prompt files, so a new install gets the same prompts, from the files.
- **The shipped chat prompt had garbled punctuation.** `prompts/behaviour.default.txt` carried fifteen mis-decoded characters (`â\x80\x94` for an em dash, `â\x86\x92` for an arrow), which went to the model as junk. Repaired; a test checks every shipped prompt.
- **The status bar reported the previous bot.** After a restart it showed the old process's model and uptime until the new one wrote its first status. A status file older than the running bot is ignored, and the LLM and SD dots are grey until the bot has reported.
- **Picking a member in the database explorer matched nothing.** The API sent Discord IDs as JSON numbers, and a browser reads those as doubles: `123456789012345678` arrived as `123456789012345680`. The page showed the wrong ID and sent it back as the filter, so "Pick user" and "Pick profile" returned no rows for nearly every member. Every ID the dashboard API returns is now a string, and the filters compare integers against the indexed columns.
- **The dashboard no longer needs the internet to load.** React came from unpkg and Pico CSS from jsDelivr on every visit. When unpkg was slow the page rendered as an empty background with no message. Both are now served from `web/static/vendor/` (React 18.3.1, Pico 2.1.1, unmodified).
- **Archived messages are listed in the order they were sent.** The explorer sorted by `created_at`, which is when a scan inserted the row, so anything a backfill added came out in insert order. It sorts by message ID now. A search for `100%` or `snake_case` also matches those characters instead of treating them as wildcards.
- **The env editor's Save writes only the fields you changed.** It posted all 200 fields each time, which sent `BEHAVIOUR` and the other long prompts through the env writer on every save; the dashboard's "Save catalog + restart" did the same with every variable. Both now send the changed keys alone, `POST /api/env/save` reports which were written and which emptied ones were skipped, and the page says so. Tokens and passwords are password fields with a Show button.
- **"Pause stream" pauses the live log.** The socket's handler kept the value the switch had when the page loaded, so the button changed its label and nothing else.
- **Vision descriptions are shown whole.** `media/images/index.jsonl` cuts a description at about 110 characters; the rest is in `media/messages.jsonl`. The image list now joins the two (cached until either file changes) where the page used to re-read the whole message log for each image clicked.
- **Smaller dashboard fixes.** The overview's stat strip was a single column because its `grid-template-columns` was invalid CSS. The three section headers under it were solid blue bars with an emoji arrow, from Pico styling `role="button"`. The status bar slid under the page nav when scrolled (a fixed 56px offset against a nav that is taller). The log filter's placeholder sat on top of its search icon. Loop cards said "379h 59m ago" and "1 replies". Profile and scan times were shown in UTC with no label; times across the dashboard are local now.
- **The installer's "Launch now?" step works on a fresh clone.** It ran `run_all.py` with the Python that ran the wizard, which on a new machine has none of the bot's dependencies, so the default answer ended in `No module named uvicorn`. `installer/steps/s08_handoff.py` now execs `.venv`'s interpreter from the repo root, and declining prints the same command (`.venv/bin/python run_all.py`).
- **`install.py --resume` no longer writes `<set in earlier step>` as the Discord token.** Secrets are scrubbed to that placeholder in `.install-state.json`, and a resume past the Discord step carried the placeholder into `.env-stable`. The Bluesky app password took the same path. A resumed run now reads secrets back from the `.env-stable` it already wrote, or runs the step that collects them again with the other answers as defaults. The write step refuses to write the placeholder, and a config that already contains it gets the token prompt again.
- **A stray Enter no longer ends the wizard.** A blank answer at a choice with no default (the model picker) raised `WizardAbort`. It asks again now. Closed stdin still aborts, and it also aborts at a required free-text prompt, which used to loop on "value required" forever. An abort prints the `--resume` command.
- **Re-running the installer keeps the settings it doesn't ask about.** "Reconfigure" rendered `.env-stable` from the example, which reset the persona, `MAX_TOKENS`, the colours and every other setting to the template's values and dropped hand-added keys, while the printed diff listed only the wizard's own keys. An existing `.env-stable` is now its own template. Each prompt defaults to the current value, features declined in step 1 are written as `false`, and a config with nothing to change is not rewritten. `parse_existing` decodes `\"`, so the daily-post channel map survives a re-run.
- **Fresh installs get the RAG settings the template states.** `RAG_TOP_K`, `RAG_CONTEXT_MAX_CHARS` and `RAG_KEYWORD_GLOBAL_FALLBACK` carried inline comments in `.env-stable.example`. The web panel's `parse_env` keeps everything after `=`, and under `run_all.py` its values are the ones the bot gets, so `int("6    # vector chunks ...")` failed and the bot ran with 10 chunks, 10,000 characters and the global fallback on (the template says 6, 4,000 and off). The comments are on their own lines now, and `tests/test_env_template.py` fails if python-dotenv and `parse_env` ever read the template differently.
- **Non-ASCII characters in quoted `.env-stable` values reach the bot intact.** `parse_env` ran `unicode_escape` over the string, which reads its UTF-8 bytes as Latin-1, so the em dash in the default `BEHAVIOUR` arrived as three junk characters. Takes effect at the next web-panel restart.
- **Dry runs leave no state file.** `install.py --dry-run` recorded all eight steps as completed, so a following `--resume` reported "nothing to do" with nothing installed. Verify-only no longer copies the whole `.env-stable` into the state file either.
- **Smaller installer fixes.** The Python version is checked before the first question (it was step 2). A `.venv` directory with no pip in it, which a failed `python -m venv` leaves on Debian/Ubuntu without `python3-venv`, is rebuilt, and the failure message names the package. The image-generation menu lists only the backends the machine can run, and hides CUDA above Python 3.12 because `torch==2.4.0+cu118` has no wheels there. A local Stable Diffusion server that isn't running yet no longer fails verification, and the handoff prints its launch command. Docs say `python3 install.py`, since macOS has no `python`.
- **A reply that opens with a clock time is no longer cut at the colon.** `remove_all_before_colon` strips a leading `name:` prefix of up to three words, and "its 3:14 am and youre still up" matched it, going out as "14 am and youre still up". The pattern now refuses a colon followed by a digit. Latent before, certain once Soupy can tell the time.
- **Link cards for MSN articles had no thumbnail, no date and no text.** msn.com serves a JavaScript shell to anything that isn't a browser: 43 KB, `<title>MSN</title>`, no `og:` tags at all, for every user agent the og:image fetcher tries (Facebook's and Slack's crawlers included). So a cross-posted MSN link got a card with no image, `_estimate_article_age_days` had nothing to read ("Published: unknown"), and trafilatura extracted 0 characters, leaving the commentary to be written from the headline alone. The article underneath belongs to someone else and MSN's own content endpoint gives up their URL, so the new `soupy/msn.py` resolves `msn.com/.../ar-<id>` to `sourceHref` and both article cogs swap it in at discovery. For the 2026-09-20 post that means kotatv.com instead of MSN: a 100 KB jpeg thumbnail, a real publish time, and 2,411 characters of article text. The endpoint is undocumented, so every failure path (non-article link, bad response, timeout, a `sourceHref` pointing back at MSN) returns the MSN URL and behaves as before.
- **Share images with query parameters were fetched with their HTML entities intact.** `_fetch_og_image` took the `og:image` content straight out of the page, so `?auth=sig&amp;width=1200` went to the CDN verbatim; signed URLs (Gray TV, Arc) answer that with HTTP 400 and the post lost its thumbnail. The URL is now decoded before the fetch, in a pure `_extract_image_url` that also covers the twitter:image and `link rel=image_src` fallbacks.
- **Soupy no longer replies to a post it already quote-posted.** On 2026-09-20 it quote-posted Jacob Soboroff's post at 15:52 and replied to the same post at 16:03. Reply discovery filtered candidates against the comment history alone (`commented_uris`), so anything it had quote-posted was still fair game for a reply; the repost pipeline had the matching filter for reposts, making the gap one-directional. `_discover_posts` now filters on `_engaged_uris`, which covers replies and quote-posts both ways. The author recency block (the one that stops it hitting the same account twice in a row) counted replies only, so the same author wasn't held back either; it now reads both buckets, newest first, via `_recent_engagement_authors`. Manual `/soupysky` with an explicit URL still overrides, as before.
- **Soupy's self-document had stopped growing and had lost three of its four sections.** The nightly reflection had the model rewrite the whole document with a 4,000-token output cap. On the main server the document hit that cap by 2026-08-12 at the latest and came back at almost exactly 19,330 characters every night after: it ended mid-sentence, only "opinions and stances" was left (relationships, running jokes and self-knowledge had been squeezed out, so ranc1d was mentioned five times and most members never), nothing was dated, nothing had been archived since April, and the reflection kept only the last 60 replies a day. Replaced by Soupy's memory (see Added). The reflection loop, its accumulator (`data/self_md/accumulator.jsonl`, now unused), the core and anchor distillation calls, and `add_notable_interaction` are gone.
- **Chat replies no longer take turns with profile passes.** The gate's lock is fair, so during the rebuild each queued reply waited behind a whole pass (54 s to 3 min 21 s observed on 2026-09-15, and up to 4–5 min when a pass loops), and a burst of three messages meant three passes. `ChatQueue` now tracks replies that are queued or running, and the profile builder waits before every LLM call until none are pending and 60 s have passed since the last reply. A pass already running is never aborted (LM Studio can keep generating after a disconnect, which would overlap the reply), so the first message of a conversation can still wait out one pass; follow-ups don't. Tests cover the wait, its 15-minute give-up, the heartbeat during a long wait, and that the pending count stays balanced when a reply raises.
- **Profiles no longer contain the prompt's own examples as facts.** The old schema prompt used real-sounding details as examples, and the model copied them: "Agatha All Along" was in 9 of 28 profiles on the main server though only one member ever mentioned it, and a member was credited with cats that appear nowhere in the archive. Examples are now fictional with invented names, and `apply_edits` drops any added item that uses an example's invented name the source messages never contain, or that copies an example nearly verbatim.
- **Profile merges no longer cut large profiles off mid-JSON.** The merge prompt truncated the stored profile at 14,000 characters, and 8 of 28 profiles were larger, so the model never saw their relationships, channels, or work sections while rewriting them. Updates are now a small edit list (add / update / remove by item id) applied in code; the model sees the current profile as compact id-tagged lines and never re-emits it.
- **The profile builder budgets against LM Studio's real window.** It assumed a 22k window by default regardless of what was loaded, and its truncation retry doubled `max_tokens` without shrinking the prompt. The window is now read from LM Studio (`/api/v0/models` → `loaded_context_length`), prompt + output stays under `USER_PROFILE_CONTEXT_SAFETY` (85%) of it, the chars-per-token estimate is recalibrated from each response's `usage.prompt_tokens`, and every failure (overflow, truncated output, timeout) halves the batch of messages instead of growing the request.
- **Chat replies get the profile items that matter, whole.** The profile prefix was the overview plus sections joined with commas and cut mid-sentence at 2,000 characters, in insertion order, so a question like "what's diego's psychological profile" got the overview and half of the personal-facts list. Items are now picked by relevance to the message and then round-robin across sections newest-first, rendered whole with their month (`(Mar 2025)`), within 3,000 characters per member (`RAG_PROFILE_MAX_CHARS_PER_USER`, block cap `RAG_PROFILE_MAX_CHARS` now 4,000). "Lately" items unconfirmed for 90 days and the "unsure" list are never shown.
- **The `[RAG] profile :` log line no longer always says `none`.** Its regex expected `(id N):` but the sketch header puts `(updated Nd ago)` in between, so every reply logged `none` even though the profile was sent.
- **A running image generation no longer silences the bot everywhere.** Chat replies were enqueued onto `bot.sd_queue` — the *same* single-consumer queue as `/sd`, `/flux`, `/img2img`, `/outpaint`, and every remix button. Because that consumer awaits each job to completion before pulling the next, one `/flux` generation blocked every reply bot-wide, across all channels and all guilds, for as long as it ran — tens of seconds to minutes on a local mflux backend. Worse, there was no sign of it: the typing indicator is opened *inside* `process_chat_message`, which hadn't been called yet, so the channel showed nothing at all — not typing, not a placeholder — until the image finished. Chat now rides its own `ChatQueue`; both it and `SDQueue` derive from a new `_WorkQueue` base holding the shared put/get/size/shutdown mechanics. Nothing was lost by splitting them: chat talks to LM Studio, image generation talks to the SD/flux server, and in the usual deployment those are different machines — the coupling was incidental, not a resource guard (verified: `process_chat_message` touches no image backend, and the shared queue was protecting no global state, since `image_descriptions` is copied at enqueue time). The chat queue stays single-consumer, so replies are still processed one at a time — ordering is preserved and N concurrent best-of-`CHAT_NUM_CANDIDATES` fan-outs can't stampede LM Studio.
- **An LLM outage no longer turns the once-daily musing into an all-day retry storm.** `last_handled_date` was written *after* `await self._run_and_post(...)`, so any exception on the way — LM Studio down, a `sqlite3` error, `channel.guild.id` on a non-guild channel — skipped the write and left the 60-second loop retrying. A musing scheduled for 06:15 meant roughly 830 failed generation attempts before the 20:00 branch finally marked the day handled, which is precisely what the adjacent comment claimed to prevent. The write now happens in a `finally`, and `last_handled_status` records which failure occurred. This does mean a transient failure at the scheduled minute costs the day's musing; that's the intended trade.
- **A musing scheduled near the end of the window is no longer silently dropped.** The past-window check ran *before* the schedule was read, so a musing due at 19:59 was discarded by any tick landing after 20:00 — and the log said the bot had booted late rather than that a due post was dropped. The check now allows a 10-minute grace past the window close, which covers loop drift while still skipping a bot that genuinely booted after hours.
- **A failed state-file write no longer produces a musing every 60 seconds, forever.** `_save_daily_state` swallowed every exception at DEBUG (invisible at the default INFO level) and the state had no in-memory mirror, so with `data/` read-only or the disk full, each tick re-read `{}` from disk, re-rolled a schedule, posted, and failed to persist again. The state is now cached in memory and authoritative once loaded, so a persistent write failure degrades to "state is lost on restart" instead of 1440 posts a day. Write failures log at WARNING.
- **Bad musing-window config no longer silently kills the loop.** `MUSING_HOUR_MAX=24` (the natural way to say "until midnight") raised `ValueError: hour must be in 0..23` on every tick, and an inverted pair raised `empty range for randrange()` — both caught by the outer handler and logged, so musings just stopped with no obvious cause. Hour 24 is now valid, and an inverted pair falls back to the 06:00–20:00 default with a warning.
- **A corrupt `data/musings_daily_state.json` no longer wedges the day.** `datetime.fromisoformat(state["scheduled_at"])` guarded only `ValueError`, but a non-string value raises `TypeError`, and a *naive* timestamp parsed fine and then raised `TypeError` at the aware/naive comparison. Both are handled: non-strings roll a fresh time, naive timestamps are localized.
- **`/soupystock` no longer returns a confidently wrong company.** `_score_search_hit` gave any dot-free `Common Stock` hit a baseline of 4 with zero query relevance, so the "reject if nothing scores above 0" guard virtually never rejected a US listing — a query Finnhub had no real match for still resolved to whatever unrelated US common stock came back first. Relevance now leads and gates: it's the fraction of query words appearing as whole words in the hit's description (so "tesla motors" → "TESLA INC" still matches on a partial name, where the old exact-phrase regex did not), an exact symbol match counts as full relevance (a ticker query shares no words with its own company name), and zero relevance is rejected outright. The structural signals — plain US ticker, common-stock type, a description *starting* with the query — only break ties.
- **A stale entry in `_NAME_ALIASES` is no longer an unrecoverable dead end.** The alias map returned its hardcoded ticker unconditionally, skipping both the `/quote` validation the ticker path uses and the `/search` fallback — so if the alias were wrong, renamed, or delisted, the user got "no live quote" forever, even after Finnhub's index caught up and `/search` would have answered correctly. Aliases are now validated exactly like a user-typed ticker and fall through on failure.
